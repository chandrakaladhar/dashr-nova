# Catalog

What each folder and file in this repo is for. Keep it current: a change that
adds, removes or repurposes a file updates this catalog in the same change.

**Runs in** says which process loads the code:

- **web**: the Next.js server (`npm run dev` / `npm start`).
- **worker**: the orchestrator worker (`npm run worker`).
- **both**: shared code that each process imports and runs in its own memory.
- **build**: tooling, CI, packaging. Nothing at runtime.

Each folder is a URL. Only the web server loads this folder. Keep logic out
of here: routes parse the request, call `lib/`, and render or return the result.

| Path | Runs in | What it is |
|---|---|---|
| `app/layout.tsx` | web | Root HTML layout. Loads `globals.css`. |
| `app/globals.css` | web | All styles (no CSS framework). |
| `app/page.tsx` | web | Home page `/`: version, dependency status, link to Projects. |
| `app/projects/page.tsx` | web | `/projects`: list of projects. |
| `app/projects/new/page.tsx` | web | `/projects/new`: page shell for the create form. |
| `app/projects/new/ProjectForm.tsx` | web (browser) | Client component: the create-project form, showing field and policy errors. |
| `app/projects/[id]/page.tsx` | web | `/projects/<id>`: project detail with status for project, entitlements, services and members. |

| `app/projects/actions.ts` | web | Server actions: `createProjectAction`, `setDevIdentity`, `acceptTermsAsAction`. |

## `lib/`: shared domain and infrastructure code

No framework entry points live here. Both processes import from `lib/`; each
gets its own instances (its own DB pool, its own Temporal client).

| Path | Runs in | What it is |
|---|---|---|
| `lib/config.ts` | both | The config contract: every env var, validated with zod. `getConfig()`. |
| `lib/db.ts` | both | `getPool()`: one Postgres pool per process. |
| `lib/errors.ts` | both | Domain errors (400/401/403/404/409/422/503) and `errorResponse` to turn them into HTTP. |
| `lib/context.ts` | web | `RequestContext` (who is calling) and the shape sent to OPA. |
| `lib/session.ts` | web | `currentContext()` for pages and server actions (dev cookies today). |
| `lib/auth.ts` | web | Dev identity from headers, and `authorize()` for the simple `dashr/authz` check. |
| `lib/opa.ts` | web | `isAllowed()`: yes/no OPA query used by `authorize()`. Fails closed. |
| `lib/policy.ts` | both | `evaluate<T>(path, input)`: fetches a structured decision from OPA (allow plus violations). |
| `lib/dependencies.ts` | web | Reachability checks for database, Temporal and OPA. |
| `lib/projects.ts` | web | Project use cases: `createProject`, `listProjects`, `getProject`. Validation → policy → transaction → outbox. |
| `lib/outbox.ts` | both | Transactional outbox: `enqueue` (in the transaction), `dispatch`, and `dispatchPending` (sweeper). |
| `lib/temporal/shared.ts` | both | Names both sides must agree on: task queue, workflow ID scheme, signal name, status types, plan shape. No SDK imports. |
| `lib/temporal/client.ts` | both | Temporal client: `startProjectProvisioning`, `notifyTermsAccepted`. Starts and signals by name. |
| `lib/provisioning/catalog.ts` | both | The provisionable services (rds, ais, asteria, redcap, apollo): roles, dependencies, sync mode; `buildStages`. |
| `lib/provisioning/contract.ts` | both | TypeScript mirror of the provisioner contract (requests, results, manifests). Must match `dashr-provisioning-common`. |

## `orchestrator/`: the orchestrator worker

One process, the orchestrator worker (`npm run worker`). The web server never
loads this folder. `workflows/` stays a separate subfolder because it is the
whole of what `workflowsPath` bundles into Temporal's deterministic sandbox:
nothing under it may do I/O or import app code other than
`lib/temporal/shared.ts` and `lib/provisioning/contract.ts`.

| Path | Runs in | What it is |
|---|---|---|
| `orchestrator/worker.ts` | worker | Entry point. Connects to Temporal, registers the workflows and activities on `dashr-nova-orchestration`, runs the outbox sweeper every 15 s. |
| `orchestrator/workflows/index.ts` | worker | The list of workflows the worker registers. |
| `orchestrator/workflows/project-provisioning.ts` | worker | `projectProvisioning`: entitlements first, then services in parallel stages, then waits for terms acceptance and syncs. Deterministic: no I/O, only child workflows and activities. |
| `orchestrator/activities/project-provisioning.ts` | worker | The workflow's side effects: load the plan, write statuses to the DB, check member eligibility with OPA. |

## `specs/`: spec-driven development

The source of truth for behaviour. See `specs/README.md` for the workflow.

| Path | What it is |
|---|---|
| `specs/README.md` | How specs, changes and decisions fit together. |
| `specs/constitution.md` | Non-negotiable principles (I–XI) that every design is checked against. |
| `specs/capabilities/<name>/spec.md` | Current behaviour, as numbered requirements: `project-creation` (REQ-PRJ), `project-provisioning` (REQ-PROV), `access-control` (REQ-AUTHZ), `operations` (REQ-OPS). |
| `specs/changes/NNNN-<slug>/` | A change in progress: `proposal.md`, `spec-delta.md`, `design.md`, `tasks.md`. |
| `specs/changes/0001-workflow-run-tracking/` | Proposed: record every workflow run, and reconcile stuck ones. |
| `specs/changes/0002-require-app-env/` | In progress: `APP_ENV` is required, so development identities are never on by default. |
| `specs/archive/` | Finished changes, moved here by `/spec-archive`. |
| `specs/decisions/NNNN-*.md` | Architecture decision records (ADRs 0001–0006). |
| `specs/contracts/openapi.yaml` | The HTTP API contract, with `x-requirements` linking operations to requirements. |
| `specs/contracts/redocly.yaml` | Lint rules for the contract. |
| `specs/contracts/README.md` | Contract rules (additive changes only). |
| `specs/templates/*.md` | Templates for specs, proposals, deltas, designs, tasks and ADRs. |
